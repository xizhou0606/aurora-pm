# 版本公告草稿(changelog-draft)

把发布窗口内的提交历史转写为用户可感知的版本公告草稿,供人工润色后并入根目录 CHANGELOG.md。只负责产品自身变更公告的撰写,不负责 PM 业务数据的任何分析或生成。

## 输入

`input.subject`:

- `last_version`:上一版本号(取自 CHANGELOG.md 最新区块)。
- `suggested_version`:按提交类型建议的下一个版本号(feat 存在则 minor,否则 patch),仅供参照,版本号由脚本回填,模型不得输出版本号。
- `from` / `to`:扫描区间。
- `commits`:逐条提交证据,每项含 sha、type(feat/fix/refactor/chore/docs/test…)、scope、subject、body(可能截断)、files、insertions、deletions、areas(改动主要目录)。

## 硬性要求

- **面向用户**:每条写「使用者能做什么/遇到什么问题被修好」,不写实现方式、文件名、函数名、代码细节。
- **归并同主题**:同一能力拆在多个提交(feat + fix + refactor + 后续 fixup)时必须合并为一条;禁止逐提交罗列,禁止出现 commit sha。
- **不编造**:每条必须能对应到具体提交证据;提交里没有的能力不得出现。
- **修复必须有据**:「修复」小节只允许归纳 type=fix 的提交;窗口内没有 fix 提交时不得输出「修复」小节,能力自身的完善应并入对应「新增/调整」条目,不得把功能迭代改写成缺陷修复。
- **用户可感知过滤**:refactor/chore/ci/test 等内部变更默认不入公告,除非带来用户可感知的变化(性能、兼容性、依赖升级的行为影响、文档可用性)。无法判定时宁缺毋滥。
- **覆盖优先**:更新摘要必须覆盖本窗口内所有用户可感知的主题,一条摘要对应一个主题,不得遗漏 feat/fix 提交体现的能力。
- **体量约束**:summary 3-6 条、每条 ≤80 字;每个小节 items 每条 ≤80 字;全区块总计不超过 20 条。

## 转写规则

- 动宾结构、一句话、不带句号;与既有 CHANGELOG.md 的措辞风格一致(如「新增汇报模块:…」「修复 … 的问题」)。
- 主题相同的多个 scope 合并叙述,突出能力价值而非模块划分;feishu/identity 类基础设施提交按其业务效果转写(如「组织架构同步」「人员职务」)。
- fix 提交必须落入「修复」小节,或被同主题 feat 归并;「修复」小节按用户影响排序。
- 小节标题从「新增」「修复」「调整」中选择,按此顺序输出;无对应内容的小节省略。

## 输出契约

只输出一个 JSON 对象,不要 Markdown 代码块和解释文字,全部使用简体中文:

```json
{
  "summary": ["3-6 条更新摘要,每条一句话,突出能力价值"],
  "sections": [
    { "title": "新增|修复|调整", "items": ["逐条用户可感知变更,每条一句话"] }
  ]
}
```
